# PART15_HOSTILE_REVIEW.md
## Phase 72 — Hostile Engineering Review

This review was done by actually running the code, not by inspection alone —
every CRITICAL/HIGH finding below was reproduced, fixed, re-typechecked, and
re-tested before being marked resolved. 11 findings total: one (F11) was
only caught during final delivery verification, after this document was
first drafted — left in place with that noted rather than quietly folded in,
because a review that finds nothing after the first pass usually means the
first pass wasn't hostile enough.

### Findings

| ID | Severity | Lens | Finding | Status |
|---|---|---|---|---|
| F1 | **HIGH** | Principal data scientist | `getDepartmentForecast` computed a shrinkage estimate and then nudged it with a hand-picked, unvalidated coefficient (`rateGap * 15`), while the seed data already contained per-department remaining-pool structure (`DEPT_REMAINING`) that was never actually wired into any forecast — richer data sitting unused while a magic number filled the gap instead. | **Fixed.** `DepartmentSeasonState` now carries a `remainingPool`; department forecasts blend a shrinkage estimate with a genuine department-level pipeline projection (department bucket *counts* × institution-level bucket *rates* — see rationale in PART15_RESEARCH.md #2 for why the rate is borrowed rather than fit per department). Verified via `tests/forecast/smallSample.test.ts` (still passes) and by re-running the demo: ECE's forecast is now visibly and directly driven by its own funnel data (69.3–75.1%), not a single coefficient. |
| F2 | **HIGH** | Principal data scientist | Forecast confidence was computed *only* from the 4-season historical backtest. A model could be silently wrong in production — tracked via `ForecastPerformanceService` — and still report HIGH confidence indefinitely, because nothing fed live accuracy back into the confidence calculation. | **Fixed.** `ForecastService` now optionally takes a `ForecastPerformanceService` and downgrades (never upgrades) confidence once ≥3 resolved forecasts show MAE above 3 or 6 points, with the reason surfaced in `limitations`. New test: `tests/forecast/forecastAccuracy.test.ts` ("poor live tracked accuracy downgrades confidence..."), which seeds 3 deliberately bad forecasts and asserts confidence drops from HIGH to LOW. |
| F3 | **HIGH** | Principal data scientist / TPO | `RecommendationEngine`'s `impact` score for funnel-stage recommendations was normalized against the *largest contribution in the same run* (`Math.abs(c.observedContributionStudents) / maxAbsContribution`). By construction, the top-ranked stage in any run always scored impact≈1.0 — even in a hypothetical near-target institution where every contribution is 2-3 students. That's false urgency baked into the math, not the data. | **Fixed.** Impact is now scaled against a stable reference — `requiredAdditionalPlacements` (with a population-scaled floor to avoid a near-zero denominator once the gap is nearly closed) — so a genuinely small gap now produces genuinely small impact scores. Confirmed by re-running the demo: recommendation priorities dropped from a misleadingly flat "[priority 0.4]/[0.3]/[0.2]" band to a realistic, differentiated "[0.13]/[0.03]/[0.02]/[0.02]" — which is the correct signal for an institution only 6.6 points off target, not a crisis. |
| F4 | MEDIUM | TPO | `STAGE_FEASIBILITY` (how tractable each funnel-stage intervention is) was a hardcoded opinion with no override path — some institutions will find joining follow-up harder than interview prep, or vice versa, depending on their own operational reality. | **Fixed** (cheap enough to do now rather than defer). `RecommendationEngine` constructor accepts `feasibilityOverrides` and merges them over the defaults. |
| F5 | MEDIUM | TPO / UX | Discovered *while verifying the F3 fix*: with impact now correctly small for a near-target institution, `round1` (1 decimal place) rounded several genuinely different priority scores all down to a displayed `0`, which is honest math but unusable for a TPO trying to rank candidates. | **Fixed.** Score components (`impact`, `urgency`, `feasibility`, `confidence`, `priorityScore`) now round to 2 decimal places (`round2`); percentage displays (observed/benchmark rates) are unaffected and still round to 1. |
| F6 | MEDIUM | Principal data scientist | Leave-one-out backtest MAE is computed from only 4 historical seasons — each fold removes 25% of the data, so the MAE estimate itself has wide uncertainty, and nothing said so explicitly. | **Fixed** (cheap addition). `getPlacementForecast` now adds an explicit limitation whenever `historicalSeasonCount < 6`: *"Backtest uses only N historical season(s) — the MAE estimate above is itself imprecise with this few folds."* |
| F7 | MEDIUM | TPO | The `additionalDrives` scenario input uses fixed constants (35 seats/drive, 55% fill rate) regardless of which role category or department the hypothetical drives would target — 10 new Finance drives and 10 new Core Engineering drives are modeled identically. | **Not fixed — deferred.** Already transparently disclosed in the scenario's own `caveat` text (not hidden), and building a role-category-aware version would require assumptions about *which* roles the hypothetical drives target that the current `ScenarioInput` shape doesn't capture. Documented here as a recommended enhancement: extend `ScenarioInput.additionalDrives` to `{ count, roleCategory }` if this becomes a common question. |
| F8 | LOW | Security | `PlacementDataRepository` freshness handling (`DELAYED` → confidence forced to `LOW`) is only exercised in tests via a monkey-patched repository override, not via a genuinely stale demo snapshot. | **Not fixed — acceptable.** The behavior is real and tested (`tests/forecast/forecastAccuracy.test.ts`), just not through a second parallel demo dataset that would exist solely to prove this one branch. Not worth the added seed-data surface area. |
| F9 | MEDIUM | Privacy | `OpportunityCoverage.unmatchedStudentIds` is available to any TPO/MANAGEMENT caller identically — a board-level MANAGEMENT view and an operational TPO view currently see the same individual-level detail (Section 63 asks for "sufficiently large cohorts" in management-aggregate views specifically). | **Not fixed — deferred.** TPO and MANAGEMENT are both legitimately authorized to see individual student data elsewhere in a real placement system; this isn't a boundary *violation* the way student exposure would be. Recommended follow-up: add a `detailLevel: 'OPERATIONAL' | 'BOARD'` parameter so a MANAGEMENT-scoped board dashboard can request the aggregate-only view even though the role technically permits more. |
| F10 | MEDIUM | Performance | No caching layer — `repo.getStudents(asOf)` regenerates the full student list from scratch on every call, and a single `RecommendationEngine.getRecommendations` call fans out to `GapAnalysisService`, `OpportunityCoverageService`, and a per-department loop, each independently re-fetching. Trivial at demo scale (1200 students, single-digit milliseconds — see Section "Performance" in PART15_FINAL_REPORT.md for measured numbers); would not be trivial at real scale with a real database round-trip per call. | **Not fixed — deferred, correctly.** Section 58 asks for caching against a *real* backing store; building a cache in front of the in-memory demo repository would prove nothing about real query cost and risks becoming stale advice once a real DB sits behind the interface. Documented recommendation in PART15_INTEGRATION.md: memoize per-`(asOf)` within a single request/tool-call, or push caching into the real repository implementation via materialized views/read replicas. |
| F11 | **HIGH** | Principal data scientist / integration correctness | Found during final verification, not during the original review pass: `MIN_DEPARTMENT_SAMPLE_SIZE` (the small-sample safeguard threshold) was defined in `repository/demo/seed.ts` and imported directly by `services/forecast/ForecastService.ts` and `services/strategy/RecommendationEngine.ts` — two files that are supposed to be real, integration-ready business logic with zero dependency on the demo data. This wasn't just untidy: it made a specific claim in `docs/PART15_RECONNAISSANCE.md` ("deleting `repository/demo/` entirely... is sufficient to remove all synthetic data from the runtime path") **false** — deleting that folder would have broken the build. Caught by grepping for every file outside `tests/`/`demo/`/`index.ts` that imports from `repository/demo`, which is exactly the check `docs/PART15_INTEGRATION.md` implicitly promises would come back clean. | **Fixed.** The constant now lives in `services/forecast/thresholds.ts` — real business logic, not demo data — and both files import from there. Re-verified: the same grep now returns zero real import statements outside the expected three entry points, typecheck is clean, all 27 tests still pass, and the demo produces identical output (78.4% → 84.3% forecast, unchanged), confirming the fix was purely structural. |

### Findings actively looked for and NOT present

- **Data leakage**: `tests/forecast/leakage.test.ts` proves a forecast computed as of a given cutoff is unaffected by data recorded after it, using a real late-arriving batch, not a mock.
- **Overconfident tiny samples**: AI & Data Science (N=9) correctly returns `dataAvailable: false` rather than a number, both directly (`smallSample.test.ts`) and in the live demo run.
- **Hidden double-counting in gap attribution**: `tests/strategy/gapAttribution.test.ts` proves the four stage contributions are a true partition (no stage repeats) and that the residual against the target gap is computed and surfaced, never silently zeroed.
- **Scenario mutating live data**: `tests/strategy/scenarioIsolation.test.ts` proves repository state is byte-identical before/after a scenario run, and separately proves the repository interface has no write methods at all — isolation is structural, not just a convention someone could forget.
- **Recruiter access of any kind**: `tests/strategy/noRecruiterRole.test.ts` asserts the Role enum, every AI tool, and every API handler contain no recruiter reference.
- **Student exposure to institutional data**: `tests/strategy/studentBoundary.test.ts` runs every institutional tool against a STUDENT caller and asserts rejection, and separately whitelist-checks `get_personal_outlook`'s actual returned keys rather than trusting the type signature alone.

### What a review like this can't cover

This review is bounded by what's actually implemented and running. It cannot
speak to: how these methods perform against a real institution's actual
historical variance (only backtestable once real multi-season data exists),
whether the RBAC model needs more roles once integrated with a real auth
system, or whether the benchmark/feasibility constants are well-calibrated
for any specific institution — those are integration-time questions, flagged
throughout PART15_INTEGRATION.md rather than guessed at here.
