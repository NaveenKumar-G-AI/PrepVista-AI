# PART15_RESEARCH.md
## Phase 1 — Research

Each row: what was uncertain, what was found, why it's relevant, what it
changed in the implementation. Sources are paraphrased, not quoted — see each
URL for the original.

| # | Question | Finding | Relevance | Implementation impact |
|---|---|---|---|---|
| 1 | How do mature forecasting practices handle "in-progress, not-yet-closed" populations? | B2B sales forecasting has converged on **weighted-pipeline forecasting**: each open opportunity is multiplied by a stage-specific historical close probability and summed, rather than treated as either fully counted or ignored. Practitioner sources (DealHub, Forecastio, SalesHive, Saber) converge on the same formula: `Σ (value × stage probability)`, with probabilities recalibrated periodically from historical conversion data. | This is structurally identical to the placement problem: a student mid-interview isn't "placed" or "not placed," they have some probability of becoming placed by season end. | `ForecastService`'s primary method (`pipelineEstimateFromSnapshot`) is exactly this — each `RemainingPoolBucket` × its historical eventual-join rate, summed. This is Section 11's "opportunity pipeline forecast" implemented with a named, defensible methodology rather than an ad hoc weighting. |
| 2 | How should a department with very few students be forecast without either refusing outright or overstating confidence? | Empirical Bayes shrinkage is the standard answer across genomics, survey small-area estimation, and general statistics (Efron & Robbins' foundational work; Fay–Herriot model for small-area estimation; a clear applied explanation via a "Surgeon A vs Surgeon B" example on Bohrium). The estimate is pulled toward a more reliable group-level average, weighted by how much individual data actually backs it — a surgeon with 5 cases shrinks hard toward the peer average; one with 500 barely moves. | Section 21/61 ask for small-sample safeguards. A hard N-cutoff (refuse below X) is the blunt version; shrinkage is the principled version and degrades gracefully. | `services/forecast/stats.ts::shrinkTowardPrior` implements this directly; `ForecastService.getDepartmentForecast` uses it (department rate shrunk toward institution rate, weighted by department N) *and* keeps a hard floor (`MIN_DEPARTMENT_SAMPLE_SIZE = 15`) below which no number is returned at all — shrinkage alone doesn't excuse a department with single-digit N, since even a heavily-shrunk estimate implies more precision than 9 data points can support. |
| 3 | How should a forecasting method's historical error be measured without leaking future information into its own evaluation? | Standard time-series evaluation explicitly warns that ordinary k-fold cross-validation is invalid for temporally-ordered data because it can train on the future and test on the past; the accepted alternative is walk-forward / rolling-origin validation, evaluated with MAE or RMSE per fold (Towards Data Science backtesting guide; MachineLearningMastery; MetricGate's walk-forward CV reference). | Section 17/56 ask for tracked model error (MAE) without leakage. | `ForecastService.backtestBaseline` implements leave-one-season-out validation across the 4 historical seasons (predict each held-out season's final % using only the other seasons' average uplift), which is the small-N analogue of walk-forward validation — each fold genuinely never sees the season it's predicting. |
| 4 | How much should a hypothetical scenario's uncertainty differ from a live forecast's uncertainty? | Not a single canonical citation here — this follows directly from the walk-forward literature's point above: a backtested method has *measured* historical error; a scenario has *assumed* rate changes with no historical realization to measure against. Treating them as equally certain would be a category error. | Section 22/60 require real uncertainty, not decorative ranges. | `ScenarioService` widens its margin relative to the baseline forecast's own margin (`scenarioMargin = baselineMargin × 1.4 + 0.5`) and caps scenario confidence at one tier below the underlying forecast's confidence — a scenario is never presented as more certain than the forecast it's built on. |
| 5 | How to decompose a funnel shortfall into stage-level contributions without double-counting? | This is a standard sensitivity/attribution problem (one-factor-at-a-time vs. Shapley-style allocation). One-at-a-time attribution over a genuinely multiplicative funnel produces an interaction term that doesn't vanish — the literature on multiplicative decomposition (general index-decomposition methods used in energy/economics analysis, same math family) treats that residual as an expected, reportable quantity rather than an error to hide. | Section 14 explicitly: "Do not double count causal stages." | Rather than accept a hidden interaction term, `GapAnalysisService` avoids the problem at the source: the four engagement-status buckets it decomposes over are a **mutually exclusive partition** of the unplaced population (every student is in exactly one), so contributions sum exactly with no interaction term to hide. The one place a genuine residual remains — whether hitting all benchmarks would actually *close the target gap* — is computed and surfaced explicitly (`unattributedResidualStudents`), never silently zeroed. |
| 6 | What does the decision-support / uncertainty-communication literature say about presenting forecasts to non-technical decision-makers? | Reflected in general forecasting practice notes across the sources above: ranges + a named confidence tier + explicit "as of" data currency outperform a bare point estimate for decisions made under uncertainty, and stale-vs-live data status should never be ambiguous. | Sections 10/20/22/60 | Every `ForecastEnvelope` this build returns carries `range`, `confidence`, `dataThrough`, `freshness`, and `limitations` as required fields, not optional add-ons — there is no code path that returns a bare number. |

### What was deliberately *not* adopted

- **ARIMA/exponential smoothing / ML regressors** (the PM2.5 and stock-price
  sources above both benchmark these) were not used for the season-level
  baseline. With 4 historical seasons on record, there isn't enough data for
  a model family designed for dozens-to-hundreds of time steps — Section 16's
  own instruction ("do not use a complex model if baseline performs better")
  argues directly against it here. If your real institution has many more
  historical seasons, this is the first place worth revisiting.
- **A single blended "AI score"** for outreach priority or recommendation
  ranking was avoided in favor of showing every weighted component
  (Section 34 explicitly asks for this) — the trade-off is a slightly less
  tidy number in exchange for something a TPO can actually contest or trust.
