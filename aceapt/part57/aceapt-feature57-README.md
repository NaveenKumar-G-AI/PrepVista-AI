# ACEAPT Feature 57 — Personal Shortcut Library

A verified personal solving-strategy memory: students save solving methods,
the system deterministically checks whether they're mathematically sound,
tracks whether *this student* actually executes them reliably, and only
recommends a shortcut once it has earned that trust through real evidence —
never because it was saved, generated by AI, or worked once.

This is a fresh, standalone build — see **"About this build"** below for why,
and **[REPORT.md](./REPORT.md)** for a full section-by-section account of
what was implemented against the spec.

```
backend/    Node + TypeScript + Express + SQLite API (the actual intelligence)
frontend/   React + Vite + TypeScript + Tailwind UI (a client for that API)
```

## Quickstart

Requires Node 20+.

```bash
# 1. Backend
cd backend
cp .env.example .env        # fill in the blanks when you're ready (see below)
npm install
npm run migrate             # creates backend/data/shortcuts.db
npm run seed                # adds 3 verified global example shortcuts (Quarter/Half/Decimal-shift Method)
npm run demo:simulate       # optional: fake usage history so the UI has something to show — see the big warning comment at the top of this script
npm run dev                 # http://localhost:4000

# 2. Frontend (separate terminal)
cd frontend
cp .env.example .env        # optional — defaults to http://localhost:4000
npm install
npm run dev                 # http://localhost:5173
```

Open http://localhost:5173. There's no real login: the top-right "Dev
identity" field just sets the `x-dev-student-id` header the backend accepts
while `JWT_SECRET` is blank (see **Configuration** below). It defaults to
`demo-student-1`, which is who `npm run demo:simulate` populates data for.

Run the backend test suite with `cd backend && npm test` (40 tests, see
**Testing** below).

## About this build

The spec (`Feature 57 master prompt`) opens by instructing an assistant to
inspect and reuse an existing ACEAPT codebase — Features 42–56, Mistake
Intelligence, a skill graph, an AI gateway, existing auth, and so on — before
writing anything. None of that exists here: this is a clean environment with
no prior ACEAPT code, and the brief for this build was explicit — build only
what was specified, don't invent the rest, and leave integration keys and
secrets blank for you to fill in.

So this build does the next best thing: it implements Feature 57 completely
and correctly on its own, with narrow, clearly-marked seams
(`backend/src/integrations/*.ts`) everywhere the spec assumes another
feature exists. Every seam is a small interface plus a harmless stub that
returns `null`/`UNKNOWN` — wire in a real implementation by passing it in
where the stub is currently constructed (see each route/service).

## Configuration — what's left blank, and why

Per your instructions, every credential and every cross-feature identifier
ships blank:

| Where | What | Why it's blank |
|---|---|---|
| `backend/.env` | `JWT_SECRET` | No real auth system exists yet. Blank → a dev-only header fallback (`x-dev-student-id`) is used instead, and that fallback **refuses to run once `NODE_ENV=production`** — see `backend/src/api/middleware/auth.ts`. Set this before deploying anywhere real. |
| `backend/.env` | `AI_API_KEY` | AI is optional and never authoritative (see spec secs. 76-80). Blank → `NoopAIClient` is used and every AI-assisted feature degrades to "unavailable" cleanly. Fill this in and AI-drafted candidate explanations start working immediately — no code changes needed. |
| `backend/.env` | `FORMULA_SERVICE_URL`, `SKILL_SERVICE_URL`, `QUESTION_FAMILY_SERVICE_URL`, etc. | Placeholders for Features 56 / 45 / 54 and friends, which don't exist in this environment. |
| database rows | `skill_id`, `formula_id`, `question_family_id` on every shortcut | Nullable columns, not enforced foreign keys, so you can backfill them once those features exist without a migration. |
| `frontend/.env` | `VITE_API_BASE_URL` | Defaults to `http://localhost:4000` in code if unset. |

## Architecture

```
Student
  → creates/discovers a candidate strategy
  → ShortcutValidationService checks it deterministically
      (property-based test vs. the canonical formula, over random +
       boundary samples; example/counterexample checks)
  → ApplicabilityService decides APPLICABLE / CONDITIONALLY_APPLICABLE /
    NOT_APPLICABLE / UNKNOWN for a given question, from declared conditions
  → PerformanceService records each real use and recomputes a per-student
    trust state (EXPERIMENTAL → DEVELOPING → RELIABLE → TRUSTED, or
    NEEDS_REVIEW on regression) purely from that student's own history
  → RecommendationService only ever suggests something APPLICABLE and
    RELIABLE/TRUSTED, and only when it's actually faster or more reliable
    than the student's standard method, and never during formal assessment
    unless explicitly allowed
```

### Design decisions worth knowing about

The spec is a product brief, not a schema, so a couple of things needed a
concrete decision. Both are called out again in code comments where they
matter:

1. **Two different "status" concepts, on purpose.** `shortcuts.status`
   (`DISCOVERED → UNVERIFIED → TESTING → VERIFIED → NEEDS_REVIEW →
   DEPRECATED/DISABLED`) describes the *content* — is this shortcut
   mathematically sound, as a definition? `student_shortcut_states.state`
   (`EXPERIMENTAL → DEVELOPING → RELIABLE → TRUSTED`, or `NEEDS_REVIEW`)
   describes *one student's* earned trust in it. A globally `VERIFIED`
   shortcut can be `EXPERIMENTAL` for a student who's never tried it — that
   split is what makes "Save != Trust" (spec sec. 21) actually enforceable
   rather than just a slogan.
2. **Free-text "when it works" vs. machine-checkable conditions.** The
   simple personal-shortcut form (spec sec. 90) collects plain sentences,
   not structured rules. Those are stored as display-only text
   (`whenToUseText`/`whenNotToUseText`) and kept out of the Applicability
   Engine's `conditions` array — a shortcut with no *real* condition rules
   defaults to `APPLICABLE` rather than `UNKNOWN`, which is what you want
   for a shortcut nobody has formalized conditions for yet.

### What's fully implemented (P0)

Personal + global shortcuts, student-created shortcuts (always start
`UNVERIFIED`), deterministic property-based + example/counterexample
validation, declared conditions/non-applicability, the applicability engine
(including options-dependence and approximation-safety), per-student
performance tracking (accuracy, time-saved vs. a supplied baseline,
difficulty/novelty breakdowns), the full trust lifecycle including
regression detection, recall/selection/application/verification/transfer/
pressure/retention training logging, mode-aware recommendations (including
the formal-assessment restriction), analytics events matching the spec's
event list, tenant isolation, RBAC (student/trainer/content_reviewer/admin),
and a private-by-default personal library.

### What's partial (P1) or intentionally out of scope (P2)

- **Discovery is a real but simple heuristic** (`discoveryService.ts`):
  it accumulates evidence per (student, family, method-signature) and
  flags a candidate "ready to test" past a threshold. A production version
  would do actual behavioral clustering across attempts, which needs a real
  attempt pipeline this build doesn't have.
- **Training content reuses each shortcut's own stored examples/
  counterexamples** rather than generating fresh questions — real question
  selection belongs to Features 53/54.
- **Cohort analytics, trainer dashboards, and content-gap reporting**
  (spec secs. 166-169, 243-244) aren't built — they're natural extensions
  of `analytics_events`, but building a real dashboard felt like the wrong
  place to spend effort on a backend-first deliverable.
- **P2 items** (autonomous discovery, handwriting/voice input, AI-assisted
  proofs, predictive misuse detection) aren't attempted — the spec itself
  frames these as "architect for," not "build."

## Testing

```bash
cd backend && npm test
```

40 tests across 7 files, all passing as of this build. Coverage includes:
the validation engine actually catching a mathematically wrong shortcut (not
just a happy path), the trust state machine refusing to trust after one
success and correctly detecting regression, the applicability engine's
options/approximation edge cases, tenant isolation and RBAC at the HTTP
layer, and a check that a shortcut's own text can't talk the system into
trusting it (see "Prompt-injection defense" below).

## Security notes

- **Auth** is a real JWT check when `JWT_SECRET` is set, with a dev-only
  header fallback that hard-refuses to run in production (see
  `backend/src/api/middleware/auth.ts`).
- **Tenant + ownership scoping** happens on every query — a personal
  shortcut is only visible to its owner; cross-tenant access returns 404,
  not 403, so existence isn't leaked either.
- **Prompt-injection defense**: shortcut text (name, description, student
  notes) is stored and displayed as inert data. Nothing in this codebase
  ever concatenates that text into a system prompt or lets it influence
  validation/trust logic — validation only ever looks at the `expression`/
  `canonicalExpression`/`examples` fields, and trust is computed purely from
  recorded usage rows. The one AI call this codebase makes
  (`integrations/aiClient.ts`) explicitly instructs the model to treat the
  student's text as untrusted data, not instructions, and its output is
  never written back as an authoritative field.
- **Input validation** is via `zod` on every mutating route.

## File tour

```

  db/schema.sql            All tables, with spec section references inline
  domain/                  Enums + shared types (ConditionRule, QuestionContext, ...)
  services/
    validationService.ts   Property-based math validation (the core engine)
    applicabilityService.ts  APPLICABLE / CONDITIONALLY_APPLICABLE / NOT_APPLICABLE / UNKNOWN
    trust.ts                The trust-state machine (pure function, heavily tested)
    performanceService.ts   Records usage, drives trust.ts, detects regression live
    regressionService.ts    Batch re-scan (e.g. after a question gets invalidated upstream)
    discoveryService.ts     Behavioral-pattern evidence accumulation
    recommendationService.ts  Mode-aware, never "always use", never speed-only
    trainingService.ts      The 7 training activity types
    libraryService.ts       Orchestrates the above into the student-facing API shape
  integrations/             Stub clients for Features 45/49/54/55/56/Mistake Intelligence + AI
  api/                      Express app, routes, auth/RBAC/error middleware
  scripts/demo-simulate.ts  Dev-only fixture generator (see the big comment at its top)

  components/               ShortcutRow/DetailPanel, AddShortcutForm, Discovery banner,
                             RecommendationPlayground, TrainingCenter, mode switcher
  App.tsx                   Ties it together: library / try-a-question / training tabs
```
