### Sales / Solution / Pre-Sales Engineer — sales_engineering · cse/ece/eee/mech · product/core/general · fresher→
Bridges technical products and customers; sells with technical credibility.
**STACK** — Core (5): **product/technical knowledge** (the product's domain, architecture, use cases) · **communication & presentation** (demos, explaining tech simply) · **solution selling** (discovery, mapping needs → solution, objection handling) · **customer/stakeholder skills** · business acumen (ROI, value). Tools (3): demo tools · CRM · presentation. Emerging (2): technical POCs · AI/cloud solutioning.
**ROUNDS** — technical/product → demo/presentation → situational selling case → behavioral.
**ASKABLE** — *Product/technical:* `[M]` explain <a technical concept/product> to a non-technical buyer; how does <product/tech> work; competitive differentiation. `[H]` architect a solution for a customer's needs; handle a technical objection. *Demo/presentation:* `[E]` sell me <this product/pen>. `[M]` run a discovery (what questions); tailor a demo to a persona; present value/ROI. `[H]` handle a skeptical technical audience. *Situational selling:* `[M]` a customer says "it's too expensive / a competitor is cheaper" — respond; qualify a lead; map pain → solution. `[H]` complex multi-stakeholder deal; POC strategy. *Behavioral:* handling rejection; a deal you'd approach differently; why sales-engineering.
**STRONG/WEAK** — Strong: technical credibility + clear communication + customer-centric selling + resilience. Weak: either too technical (no selling) or too salesy (no depth). **RED FLAGS** — can't explain tech simply; no discovery/objection handling; pushy without listening.

### Technical Account Manager / Customer Success Engineer / Field Application Engineer (FAE) — sales_engineering · cse/ece/eee · product/core · fresher→
Post-sale technical relationship / hardware field support.
**STACK & QUESTIONS** —
- **TAM / CS Engineer:** core: product depth, troubleshooting, customer relationship, account health, communication, technical + business. `[M]` onboard/support a customer technically; troubleshoot an issue; drive adoption; manage an escalation; communicate a fix. `[H]` reduce churn via technical value; handle a critical outage with a customer.
- **Field Application Engineer (FAE):** core: hardware/product technical depth, application support, troubleshooting on site, customer training, electronics/embedded (for semis). `[M]` help a customer design-in a component; debug a customer's hardware issue; explain specs/trade-offs; application support. `[H]` on-site fault diagnosis; design guidance for a use case.
**STRONG/WEAK / RED FLAGS** — Strong: technical depth + customer empathy + troubleshooting. Red flag: no troubleshooting method or customer skill.

### Implementation Engineer — sales_engineering/software_engineering · cse/ece/eee · service/product/general · fresher→
Deploys and configures solutions for clients.
**STACK** — Core (5): product configuration, SQL basics, troubleshooting, OS/networking basics, scripting, requirement gathering, integration. `[M]` configure/deploy a product for a client requirement; troubleshoot a deployment; integrate with a client system; data migration; SQL to validate. `[H]` complex integration; handle a failed deployment; client-specific customization.
**STRONG/WEAK / RED FLAGS** — Strong: technical + client requirement translation + troubleshooting. Red flag: no troubleshooting/requirement method.

### Technical Writer — writing_devrel · cse/aids/ece/any · service/product/general · fresher→
Creates clear technical documentation.
**STACK** — Core (5): **technical writing** (clarity, concision, structure, audience analysis) · **documentation types** (API docs, guides, tutorials, references) · **tools** (Markdown, docs-as-code, Git) · basic technical fluency (read code/APIs) · editing/style guides. Tools (3): Markdown/docs tools · Git · diagramming. Emerging (2): docs-as-code · AI-assisted writing · developer docs.
**ROUNDS** — writing sample/exercise → technical understanding → behavioral.
**ASKABLE** — *Writing:* `[E]` explain <a technical concept> in plain language; what makes good documentation. `[M]` write/outline docs for <a feature/API>; structure a tutorial vs reference; audience adaptation; simplify jargon; document a process. `[H]` improve a confusing doc; information architecture for a docs site; handle ambiguous/incomplete info from engineers. *Technical:* `[M]` read an API/code snippet and document it; what questions to ask engineers. *Process:* `[M]` your documentation workflow; docs-as-code; versioning.
**STRONG/WEAK** — Strong: clear + structured + audience-aware + can grok technical detail. Weak: verbose/unclear, can't simplify, no structure. **RED FLAGS** — can't explain a concept simply; no audience awareness.

### Developer Advocate (DevRel) — writing_devrel · cse/aids/ece · product · fresher→
Bridges a product and its developer community.
**STACK** — Core (5): technical depth (coding, the product's domain) · **communication/content** (talks, blogs, demos, tutorials) · **community engagement** (empathy, feedback loops) · developer empathy · social/public speaking. `[M]` explain/demo a product to developers; write a tutorial/blog; build a sample app; gather + relay developer feedback; handle a critical developer. `[H]` a launch content strategy; grow a community; represent developer needs to product.
**STRONG/WEAK / RED FLAGS** — Strong: technical + communication + genuine developer empathy. Red flag: no technical depth or no communication/empathy.

### Technical Support / Application Support Engineer — operations_support · cse/ece/eee/it · service/general · fresher→
Resolves customer/application technical issues.
**STACK** — Core (5): **troubleshooting/RCA** · product/technical knowledge · **OS/networking/SQL basics** · **ticketing & ITIL** (incident/problem mgmt, SLAs) · **customer communication** (patience, clarity, escalation). Tools (3): ticketing (JIRA/ServiceNow) · log/monitoring tools · remote tools. Emerging (2): observability · automation/self-service · AI support.
**ROUNDS** — technical/troubleshooting → scenario → communication/behavioral.
**ASKABLE** — *Troubleshooting:* `[E]` how do you approach an issue you've never seen. `[M]` a systematic debugging process; "app is slow/down — steps"; log analysis; SQL to check data; isolate client vs server. `[H]` a tricky intermittent issue; root-cause vs workaround; escalation decision. *OS/network/SQL:* `[M]` common commands; check a service/port; a SQL query to investigate; DNS/connectivity. *Communication (scenario):* `[E]` explain a fix to a non-technical user. `[M]` handle an angry customer; manage expectations under an SLA; when to escalate. `[H]` communicate during a major outage. *ITIL:* `[M]` incident vs problem; SLA/priority; ticket lifecycle.
**STRONG/WEAK** — Strong: systematic RCA + calm clear communication + escalation judgment. Weak: guesses, no method, poor communication. **RED FLAGS** — no troubleshooting method; can't communicate calmly; no escalation sense.

**STRONG/WEAK / RED FLAGS** — Strong: domain fundamentals + data/analysis + structure. Red flag: no metric/method understanding.
